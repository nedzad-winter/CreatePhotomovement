# GameTests — In-game tests

The tests from phase 3 run without Minecraft and check calculation logic and resources.
These ones check what really needs a world: real sky visibility, real block placement,
contraption assembly.

> **Build instructions for the test world and the manual checklist:
> [docs/test-world.md](test-world.md).** This document describes the structure and status
> of the tests; there you will find what you need to do in the client.

## The structure template

All tests share **one single** template called `solar_platform`, which is generated by a script:

```
powershell -File tools/make_gametest_structure.ps1
gradlew :neoforge:1211:runGameTestServer
```

The files are checked in; you only need the script if the size of the arena should change.
Details and the folder pitfall (`structure` in the mod, `structures` when exporting from the
game) are in [docs/test-world.md](test-world.md).

> **Correction:** This document previously contained instructions for building the template
> by hand, with the note that a `.nbt` cannot be generated from code. That was wrong and was
> carried over unverified from the original plan.

## Why Fabric does not need a template

The Fabric API provides an empty structure:
`@GameTest(template = FabricGameTest.EMPTY_STRUCTURE)`. NeoForge has no equivalent — in
21.1.206 a `@EmptyTemplate` annotation was searched for, and it does not exist there.
Hence the generated template for the two NeoForge targets.

## Structure of the tests

The test classes themselves **cannot** be shared: NeoForge requires static methods using
`net.neoforged.neoforge.gametest.*` (or `net.minecraftforge.gametest.*` in 1.20.1), while
Fabric requires instance methods and a `FabricGameTest` interface.

Instead, everything below that is shared, in
`common/src/main/java/com/createphotomovement/gametest/`: `SolarAssertions` for world setup
(time, weather) and the panel checks, `WindmillAssertions` for assembly and checks of the
bearing. The scaffolding per loader stays thin and only contains annotations and positions.

The fact that both helper classes compile for all three targets also shows, incidentally,
that `ServerLevel.setWeatherParameters`, `Level.setRainLevel`,
`GameTestAssertException(String)`, `KineticNetwork.calculateCapacity` and
`MechanicalBearingBlockEntity.assemble`/`getLastAssemblyException` are identical in 1.20.1
and 1.21.1.

There is one exception: `savedTagCarriesNoCapacity` reads the saved NBT, and
`saveWithFullMetadata` received a `HolderLookup.Provider` in 1.21. This one method therefore
lives in the test class itself and not in `common/`.

## The windmill tests

The bearing is where the most hand-written state lives: sail counts and sky visibility are
determined **once during assembly** and then held in fields, written to NBT, deliberately
zeroed on load, and recounted from the contraption's block list. Each of these steps exists
because of a capacity that was once counted twice. The formula is covered by
`WindmillOutputTest`; whether the right numbers arrive there can only be judged in a world.

Each test builds two identical bearings side by side — one with solar sails, one with
Create's ordinary sails — and compares them with each other instead of against fixed SU
values. This way the test measures the bonus and not the configuration.

| Test | Expectation |
|---|---|
| `assemblesFromSolarSails` | 9 solar sails, 0 regular, sky access, turns |
| `plainSailsAreNotCountedAsSolar` | 9 regular, 0 solar |
| `solarSailsDoubleTheCapacityByDay` | ×2.0 compared to the reference |
| `sailTypeDoesNotChangeSpeed` | same speed — the bonus is on SU, not RPM |
| `noSkyAccessMeansNoBonus` | covered: ×1.0, **but keeps turning** |
| `keepsTurningAtNight` | turns, at the same speed as the reference |
| `losesOnlyTheBonusAtNight` | ×1.0 |
| `rainReducesTheBonus` | ×1.5 |
| `thunderRemovesTheBonus` | ×1.0, keeps turning |
| `networkCapacityReturnsAfterANightDayCycle` | network capacity unchanged after two cycles |
| `speedIsUnaffectedByNightfall` | speed exactly identical over day → night → day |
| `savedTagCarriesNoCapacity` | the saved NBT contains `Capacity=0` and `AddedCapacity=0` |
| `disassemblingClearsTheOutput` | after disassembly 0 RPM **and** 0 SU |

### Mixed sails — the only scenario on all three targets

`regularSailsNextToSolarSailsCount` builds a windmill from 5 solar and 4 Create sails next
to a reference of 9 Create sails, and requires that the mixed windmill delivers more than
the reference, but less than double. It safeguards the fix that both sail types share their
groups instead of being rounded down separately.

The expectation deliberately does **not** come from `WindmillOutput` — a test that derives
its target from the formula under test passes even against a broken formula. Against the
old calculation it fails on all three targets with `0.0 vs 512.0 SU/RPM`.

The windmill is built by `WindmillAssertions.buildWindmill(..., secondSail, count)` in
`common/`; the per-target classes only contain annotations and positions.

Two things that came up during porting:

- **NeoForge 1.20.1 started in a normal terrain world.** The test server builds its world
  from `server.properties`, and its default is `level-type=minecraft:normal`. The arena lies
  at y=-60 — in a flat world that is at the surface, in a normal one deep in the deepslate.
  Nothing in it saw the sky (`skyAccess=false`), and the heightmap reported 63.
  `neoforge/1201/build.gradle` therefore writes a flat world before the start. NeoForge 1.21.1
  and Fabric do not have this problem.
- **Fabric 1.20.1 also runs Create's own game tests**, and three of them
  (`TestFluids.thresholdSwitch`, `TestItems.attributeFilters`,
  `TestProcessing.precisionMechanismCrafting`) fail in this environment.
  `gradlew :fabric:1201:runGametest` therefore ends with an error even when our own tests are
  green. The result of our own tests is in `fabric/1201/build/gametest-report.xml`.

### Rain is measurable here, not for the panels

Both are the same weather, but two different questions. The bearing asks
`level.isRaining()` — global weather, directly settable. The panels ask
`level.isRainingAt(pos)`, which additionally consults the heightmap and in a test arena
always reports "covered". Therefore rain is automated for the bearing and remains manual
work for the panels
([Check F](test-world.md#check-f--rain-and-thunder)).

### What could be automated from the restart bug — and what could not

The reported bug has a precise mechanism. On load, `KineticBlockEntity.initialize()` passes
the capacity read from NBT to the network as `unloadedCapacity` and **additionally** adds the
bearing as a live source. A saved number that was not zeroed beforehand is therefore counted
twice. The fix is one line in `write()` that sets `capacity` and `lastCapacityProvided` to 0
before serialization — and until now nothing guarded that.

`savedTagCarriesNoCapacity` guards exactly this line: it builds a real windmill with real
capacity, saves it the way the chunk would, and checks in the tag that `Capacity=0` and
`AddedCapacity=0`.

**Replaying the load process itself does not work.** I tried: save the block entity, discard
it, rebuild it from its own tag. The connection to the contraption entity then breaks
permanently — after 80 ticks the bearing still reported `solarSails=0, speed=0`. Such a test
measures the test setup, not the mod. The attempt has been removed; reloading remains
checks A through C by hand.

### Why the network capacity is measured and not the bearing's

`calculateAddedStressCapacity()` recalculates from the current fields on every call — this
value cannot contradict itself. The reported bug sat in `KineticNetwork.calculateCapacity()`,
i.e. in `presentCapacity + unloadedCapacity`, where the same bearing appeared once as a live
source and once as leftover unloaded capacity. The test therefore measures the network total.
It still does not reach a server restart — that remains checks A through C.

### Two things that surfaced along the way

**Sails only connect within their own plane.** A 3×3 area of solar sails with default
orientation on a bearing facing north broke into strips, and assembly failed with
*"Attached structure does not include enough sail-like blocks: 3"* — with nine sails placed.
The orientation of the sails must match the bearing axis. This did not show up with Create's
own sails, because their default orientation happened to fit.

**Weather does not take effect immediately.** `setWeatherParameters` only sets switches; the
game reads two intensity values that move toward their target by 0.01 per tick. `isRaining()`
requires more than 0.2, `isThundering()` more than 0.9 — so a thunderstorm needs roughly 90
ticks to become real, and the same to disappear. Since all batches share a world, my rain
leaked into the horizontal tests, which then failed with `skyDarken=5, effective=10,
needs>=12` — through no fault of their own. `SolarAssertions` now sets the intensity directly,
so the weather is a fact and not a side effect.

### Three things that went wrong on the way

**All tests ran at the same time.** GameTests of one batch share a world, and time of day
as well as weather are global state — the tests overwrote each other. Two night tests
reported different times of day. Fixed with `batch = "..."` per required world state; tests
that change the time *during* their run get a batch of their own.

**The ground layer was one level too high.** A structure block places its content one level
above itself, so template level 0 ends up at helper height 1. The vertical tests did not
notice — `setBlock` overwrites the floor, and they only look upward. The horizontal tests
looked directly into the floor layer: `front=Bedrock, frontLightBlock=15`. All test positions
are now at height 2.

**Two tests were built in a way that could not check anything.** They started a second
sequence inside a running one; the outer one calls `thenSucceed()` as soon as its block
returns. Green, without ever reaching the check. Now they are linear sequences.

Without diagnostic output in the assertions none of these three points would have been
findable — every error message now names the time of day, sky light, `skyDarken`, the block
in front of the panel, and the weather situation.

## Important: the windmill bearing does NOT stand still at night

For the solar generators the rule is "no output at night". For the solar windmill bearing
this explicitly does **not** apply:

> At night, the solar windmill generator is a completely normal windmill bearing.

So:

| | Day (clear, open sky) | Night |
|---|---|---|
| Speed | depends on the number of sails | **unchanged, same speed** |
| Solar bonus | ×2.0 | ×1.0 — drops away |
| Total SU | doubled | like an ordinary windmill with the same number of sails |

The code already does this correctly, by its structure:
`WindmillOutput.generatedSpeed(...)` takes **no** time or weather parameter at all — the
speed cannot depend on the time of day. Only `solarMultiplier(...)` knows the time, and it
affects only the stress capacity.

This is recorded in two places. Computationally in `WindmillOutputTest`:

- `stillTurnsAtNight` — same speed by day and night
- `atNightBehavesLikeAPlainWindmill` — solar sails deliver at night exactly as much as the
  same number of ordinary sails

And in the world of `SolarWindmillGameTests`: `keepsTurningAtNight` checks that a solar
windmill assembled at night runs at the same speed as the reference with ordinary sails,
`losesOnlyTheBonusAtNight` the factor ×1.0, and `speedIsUnaffectedByNightfall` the speed
across a full change.

A test that expected a standstill would pass even though the behavior is wrong — which is
why the rule is stated explicitly here and not only in the code.
