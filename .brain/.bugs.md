### Bug #2: Solar Windmill Bearing Visual Issues — Missing Top, Shadow, Dark Lighting (Fixed 2026-05-09, Issue #11)

**Status:** FIXED across all three loaders (neoforge/1201, neoforge/1211, fabric/1201)

**Severity:** Critical (Bearing top + shaft missing entirely; once visible, ghosting and severe under-lighting)

**Symptoms (in order of discovery):**
1. The bearing block rendered, but the rotating bearing top and the half-shaft on the back face were completely invisible.
2. After fixing #1, the bearing top showed a static "ghost" copy that didn't rotate with the contraption.
3. After fixing #2, the bearing top + shaft rendered far darker than Create's vanilla bearings (almost black) even with open sky overhead.

**Root Causes (one per symptom):**

1. **No Flywheel visualization registered.** Both `BearingRenderer.renderSafe` and its parent `KineticBlockEntityRenderer.renderSafe` short-circuit with `if (VisualizationManager.supportsVisualization(be.getLevel())) return;` whenever Flywheel is active (the default in modern Create). Create registers `BearingVisual` for its own `WindmillBearingBlockEntity` to take over the GPU rendering, but our `SOLAR_WINDMILL_BEARING` block entity had no visualizer registered — so when Flywheel was active (always), nothing rendered the bearing top or shaft.

2. **Static "Top" cuboid baked into the block model.** Our `solar_windmill_bearing.json` defined a cuboid named `"Top"` from Y 12-16 with the `bearing_top` texture. Create's vanilla `block/bearing/block` model deliberately leaves Y 12-16 empty — that slot is reserved for the dynamic bearing top rendered as a partial model by `BearingVisual`. Our model had both, so the dynamic one rotated while the static one stayed put, producing the ghost.

3. **Block lighting blocked sky propagation.** The `SolarWindmillBearingBlock` registration was missing `.noOcclusion()`, and even with it added the default `propagatesSkylightDown` returns `false` for blocks whose shape is `Shapes.block()` (the default). With sky light blocked at the bearing's position, `BearingVisual.relight()` queried near-zero light and rendered the partial models almost black.

**Solution:**

1. Register Create's `BearingVisual` as the Flywheel visualization for `SOLAR_WINDMILL_BEARING` via `SimpleBlockEntityVisualizer.builder(...).factory(BearingVisual::new).apply()` during client setup. Keep Create's `BearingRenderer::new` as the legacy fallback. This mirrors Create's own registration pattern for `WindmillBearingBlockEntity`.
2. Remove the entire `"Top"` element (all six faces) from `solar_windmill_bearing.json` so the partial model rendered by `BearingVisual` has clear space to occupy.
3. Add `.noOcclusion()` to the block properties AND override `propagatesSkylightDown(...)` to return `true` and `getLightBlock(...)` to return `0` on `SolarWindmillBearingBlock`. The override pair is necessary because the default `propagatesSkylightDown` checks shape and would otherwise still block light.

**Files Modified (per loader):**
- `<loader>/src/main/java/com/createphotomovement/CreatePhotomovementClient.java` — registered `BearingVisual` via `SimpleBlockEntityVisualizer`
- `<loader>/src/main/java/com/createphotomovement/AllBlocks.java` — added `.noOcclusion()` to `SOLAR_WINDMILL_BEARING` properties
- `<loader>/src/main/java/com/createphotomovement/content/kinetics/solarwindmill/SolarWindmillBearingBlock.java` — added `propagatesSkylightDown` and `getLightBlock` overrides
- `<loader>/src/main/resources/assets/createphotomovement/models/block/solar_windmill_bearing.json` — removed `"Top"` cuboid (Y 12-16, bearing_top texture)

**Learning Points:**
- When subclassing a Create block entity that ships with a Flywheel visualization, you must register the same visualization for your block entity type — inheriting the BE class isn't enough. `SimpleBlockEntityVisualizer.builder(BE_TYPE).factory(VisualClass::new).apply()` is the direct API (Create's `.visual(...)` Registrate method wraps this).
- A custom block model that copies a Create block model must omit any geometry the dynamic visual is going to render — duplicate geometry produces a static "ghost" overlay.
- `noOcclusion()` alone is not enough to allow sky light through a non-air block when the block's shape is still `Shapes.block()`. Override `propagatesSkylightDown` (and optionally `getLightBlock`) when light queries at the BE's own position must return non-zero.
- Existing block lighting in a chunk is cached — after changing occlusion semantics, players must break/replace the block (or reload the chunk) for the new lighting to take effect.

**Version Status:**
- NeoForge 1.20.1: FIXED (verified in-game)
- NeoForge 1.21.1: FIXED (verified in-game)
- Fabric 1.20.1: FIXED (code parity, not in-game tested)

### Bug #1: Solar Windmill Bearing Not Rendering (Fixed 2026-02-07)

**Status:**  FIXED

**Severity:** Critical (Visual Bug - Bearing appears static/frozen in-game)

**Location:** `neoforge/1201/src/main/java/com/createphotomovement/CreatePhotomovementClient.java:36`

**Error Message:**
``
error: cannot find symbol
    com.simibubi.create.content.contraptions.bearing.WindmillBearingRenderer::new);
                                                    ^
  symbol:   class WindmillBearingRenderer
  location: package com.simibubi.create.content.contraptions.bearing
``

**Description:**
The Solar Windmill Bearing wasn't rendering properly - it appeared static and frozen in-game without showing the contraption or animations. The code attempted to register `WindmillBearingRenderer` from Create mod, but this class doesn't exist in Create version 6.0.8-291.

**Root Cause:**
- Incorrect renderer class name used (`WindmillBearingRenderer`)
- Create 6.0.8-291 uses `BearingRenderer` as a generic renderer for all bearing types
- The specific `WindmillBearingRenderer` class doesn't exist in this version of Create
- Without proper renderer registration, Minecraft couldn't display the bearing animations or assembled contraptions

**Solution:**
Import and register the correct renderer class `BearingRenderer` from Create's contraptions.bearing package.

**Code Changes:**

**Added import:**
``java
import com.simibubi.create.content.contraptions.bearing.BearingRenderer;
``

**Renderer registration (corrected):**
``java
event.registerBlockEntityRenderer(AllBlockEntityTypes.SOLAR_WINDMILL_BEARING.get(), BearingRenderer::new);
``

**Technical Details:**
- `BearingRenderer` is a generic renderer in Create that handles all bearing types (mechanical, windmill, clockwork)
- This matches the implementation used in the working NeoForge 1.21.1 version
- The renderer properly displays bearing rotation animations and assembled contraptions
- `SolarWindmillBearingBlockEntity` extends Create's `WindmillBearingBlockEntity`, so it inherits the rendering behavior

**Testing:**
-  Code compiles successfully
-  Build completes without errors
-  In-game verification pending (bearing should now animate and display contraption)

**Files Modified:**
- `neoforge/1201/src/main/java/com/createphotomovement/CreatePhotomovementClient.java`

**Learning Point:**
When extending block entities from dependency mods like Create:
1. Check the working reference implementation (e.g., 1.21.1 version) first
2. Verify renderer class names exist in the target Create version
3. Use generic renderers (`BearingRenderer`) rather than assuming specific variants exist (`WindmillBearingRenderer`)
4. Create often uses polymorphic renderers that handle multiple block entity types

**Prevention:**
- Always verify class names against the actual Create version being used
- Check Create's API documentation or source code for available renderer classes
- Test compilation immediately after adding renderer registrations
- Compare implementations across different working versions when porting features

**Related Components:**
- `SolarWindmillBearingBlockEntity` (extends `WindmillBearingBlockEntity`)
- `AllBlockEntityTypes.SOLAR_WINDMILL_BEARING`
- Create mod version 6.0.8-291
- Minecraft 1.20.1 / NeoForge/Forge 47.4.0

**Version Comparison:**
